# 身份认证 -- Session and Cookie

Session 和 Token 是两种最主流的用户身份验证机制。简单来说，Session 是“有状态”的（服务器记得你），而 Token 是“无状态”的（服务器见票即认）。

**Session vs Cookie**
| **特性**    | **Cookie**    | **Session**      |
| --------- | ------------- | ---------------- |
| **存储位置**  | 客户端（浏览器）      | 服务器端             |
| **安全性**   | 较低（易被伪造或截获）   | 较高（存储在服务器，较难被伪造） |
| **容量限制**  | 通常每个域名 4KB 左右 | 理论上无限制（受服务器内存影响） |
| **对资源消耗** | 不占用服务器资源      | 占用服务器内存/存储空间     |
| **生命周期**  | 可设置长期有效       | 通常随浏览器关闭或超时失效    |

## 1. Session

### 1.1 工作原理 
1️⃣ **创建会话**：用户第一次访问服务器时，服务器创建一个唯一的 Session ID。  
2️⃣ **下发 ID**：服务器通过响应头（Set-Cookie），将这个 Session ID 发送给浏览器的 Cookie 存储。  
3️⃣ **后续请求**：用户再次访问时，浏览器会自动在请求头中携带这个 Session ID。  
4️⃣ **识别身份**：服务器根据 ID 在内存或数据库中找到对应的 Session 数据，从而识别用户。  

### 1.2 使用方式
#### 1.2.1 原生单机 Session (Memory Store)  

##### ✅ 核心原理

将用户的会话数据直接保存在 Web 服务器运行时的内存（RAM）中。

##### 🚧 运行流程

1️⃣ **初次请求**：客户端发送 HTTP 请求到服务器。  
2️⃣ **创建容器**：服务器在内存中开辟一块空间，生成一个随机且唯一的 SessionID。  
3️⃣ **绑定数据**：服务器将用户信息（如 user_id: 101）存入这块空间。  
4️⃣ **下发令牌**：服务器在响应头中加入 Set-Cookie: JSESSIONID=abc123...（名称随框架不同，如 connect.sid 或 PHPSESSID）。  
5️⃣ **后续识别**：浏览器下次请求自动携带该 Cookie。服务器通过这个 ID，直接从内存 Map 中精准取出对应的数据。  

##### ❌ 存在问题
**A. 无法实现负载均衡（会话丢失）**  
如果你有两台服务器 A 和 B。用户在 A 登录了，Session 存在 A 的内存里。下一次请求被负载均衡器分配到了 B，B 的内存里空空如也，用户会被强制要求重新登录。

**B. 重启即消失**  
内存是易失性存储。当你部署新代码重启服务器，或者服务器崩溃闪退时，内存中所有的 Session 都会被清空，所有在线用户都会掉线。

**C. 内存溢出风险**  
如果你的网站访问量巨大，而你没有及时清理过期的 Session，内存会被这些键值对撑爆，导致服务器宕机（OOM - Out of Memory）。

##### 使用场景
**1.个人项目/演示 Demo**：不需要安装配置 Redis，开箱即用。  
**2.小型内部系统**：公司内部几十个人用的管理后台，单台服务器足以应对，且对重启掉线不敏感。  
**3.初期创业产品**：在用户量极其有限的情况下，减少技术栈的复杂度。

#### 1.2.2 Session 复制 (Session Replication)  

##### ✅ 核心原理

服务器 A 创建了 Session 后，会通过广播或组播协议将该 Session 同步到集群中的所有其他服务器（B、C、D）。在支持 Session 复制的 Web 容器（如 Tomcat）中，通常采用 多播（Multicast） 或 TCP 单播 协议进行通信。

##### 🚧 运行流程

1️⃣ **数据写入**：当服务器 A 的 写入Session (session.setAttribute() 被调用)。  
2️⃣ **触发同步**：A 节点会立即向集群内的其他节点发出广播。    
3️⃣ **副本存储**：B 节点接收到消息，在自己的内存中创建或更新一个一模一样的 Session 对象。  
4️⃣ **失效同步**：如果用户在 A 登出，A 发出删除指令，B 也会同步删除。  

##### ❌ 存在问题
**A. 网络风暴风险**  
当集群规模变大（例如超过 5 台机器），每产生一个 Session 都要同步给所有机器，产生的网络流量呈指数级增长。

**B. 内存冗余**  
每台服务器都要存储全量集群的 Session，内存消耗极大。

**C. 序列化开销**  
数据在网络传输前需要序列化，存入后需要反序列化，频繁操作会消耗大量 CPU。



#### 1.2.4 分布式 Session (集中式存储)  

##### ✅ 核心原理

将 Session 数据从 Web 服务器中抽离出来，统一存放在高可用的 Redis 集群中。此时，Web 服务器变成了**无状态（Stateless）**的。无论请求落在集群中的哪台服务器，它们都去同一个 Redis 数据库中读写 Session。

##### 🚧 运行流程

1️⃣ **客户端请求**：用户携带 Cookie（含 Session ID）访问服务器。   
2️⃣ **拦截请求**：Web 框架（如 Spring Session）拦截请求，获取 Session ID。      
3️⃣ **读写 Redis**：(1)如果 Session ID 存在，从 Redis 中取回数据反序列化到内存；  (2)如果不存在，创建一个新的 Session 并存入 Redis。  
4️⃣ **响应返回**：业务处理完后，如果有数据变更，同步更新到 Redis。    

##### ❌ 存在问题
**A. 序列化问题**  
存入 Redis 的对象必须实现 Serializable 接口。建议使用 JSON 格式 序列化，方便跨语言（如 Java 存，Node.js 读）且易于调试。 

**B. 网络开销**  
每次请求都要访问一次 Redis。如果 Redis 部署在远程机房，网络延迟会叠加到响应时间上。

**C. Redis 压力**  
如果 Session 数据过大，会占用大量 Redis 内存。建议只在 Session 中存储必要的 ID 或用户信息，不要存储大对象。

### 1.3 方案对比
| **方案**         | **扩展性**  | **稳定性** | **开发难度** | **适用场景**    |
| -------------- | -------- | ------- | -------- | ----------- |
| **原生单机**       | 极差       | 重启即丢    | 极低       | 个人项目 / Demo |
| **Session 复制** | 差 (广播风暴) | 高       | 中        | 小型内网集群      |
| **Redis 共享**   | 极强       | 极高      | 低 (框架成熟) | 中大型互联网项目    |



## 2. JWT (Json Web Token)

`JWT` 是目前最流行的跨域身份验证方案。它是一种基于 `JSON` 的开放标准（RFC 7519），用于在各方之间以对象的形式安全地传输信息。

### 2.1 组成结构

JWT = Header（头部）+ Payload（负载）+ Signature（签名）

#### ① Header (头部)

描述 JWT 的元数据，通常包含两部分：令牌类型（JWT）和所使用的签名算法（如 HMAC SHA256 或 RSA）。 

⚠️ 该部分会经过 Base64URL 编码。
```json
{
  "alg": "HS256",
  "typ": "JWT"
}
```

#### ② Payload (负载)
包含声明（Claims），即实际传输的数据。常见声明有：
* **注册声明（建议但不强制）**：iss (发行者), exp (过期时间), sub (主题), aud (接收者)。  
* **公共声明**：自定义字段，如 userId, username, role。  
* **私有声明**：业务需要的自定义字段。  

⚠️ 这部分也是 Base64URL 编码，任何人都可以解码，所以千万不要在这里存密码或敏感信息。

#### ③ Signature (签名)
服务器使用 Header 中指定的算法，结合一个只有服务器知道的密钥（Secret），对前两部分进行哈希计算。

**计算公式**：Signature=HMACSHA256(base64(Header)+"."+base64(Payload),secret)

### 2.2 工作流程
1️⃣ **登录**：用户提交用户名密码。  
2️⃣ **签发**：服务器验证通过，生成 `JWT` 字符串，返回给客户端。  
3️⃣ **存储**：客户端将 `JWT` 存入 `localStorage` 或 `Cookie`。  
4️⃣ **发送**：后续请求时，客户端在 `Header` 中携带 `Authorization: Bearer <token>`。  
5️⃣ **校验**：服务器拿到 Token，用自己的密钥重新计算签名。如果一致且没过期，则认为用户合法。无需查数据库或 Session。
