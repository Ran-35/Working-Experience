# CSRF（跨站请求伪造）

## 1. 基本概念
攻击者通过诱导你访问一个恶意链接，利用你已经在某个网站“登录”的身份，替你发送一些你并不知情的请求。

### 1.1 攻击流程 
1️⃣ **登录受信任网站 A**：你在浏览器中登录了某银行或社交平台，且登录凭证（Cookie）尚未过期。    
2️⃣ **验证机制依赖 Cookie**：该网站完全依赖浏览器自动发送的 Cookie 来识别用户身份。  
3️⃣ **访问恶意网站 B**：你在未登出 A 的情况下，点击了攻击者构造的恶意链接。  
4️⃣ **恶意网站 B 冒用 Cookie**：页面包含一段自动执行的代码，向 网站 A 的接口发起请求。  
5️⃣ **被冒用身份**：浏览器会自动带上受信任网站 A 的 Cookie。服务器一看：“哟，凭证是真的”，于是请求成功。
### 1.2 防御办法 
由于 CSRF 利用的是浏览器自动携带 Cookie 的特性，防御的核心就在于**增加浏览器无法自动获取的验证信息**。
#### ① 引入 CSRF Token
**方法**：服务器在返回页面时，随机生成一个唯一的 Token 给客户端。客户端在后续发起请求时，必须手动在请求头或表单里带上这个 Token。

**原理**：攻击者虽然能让浏览器带上 Cookie，但由于同源策略，他们无法跨域读取你页面里的这个随机 Token，所以请求会被服务器拒绝。

#### ② SameSite Cookie 属性
**方法**：在设置 Cookie 时增加 SameSite 字段：
(1)Strict：完全禁止第三方网站请求携带 Cookie。  
(2)Lax（默认）：仅在导航到目标网址的 GET 请求中允许携带。  

**原理**：从根源上限制了跨站请求时 Cookie 的发送

#### ③ 验证 Referer / Origin 头部
**方法**：服务器检查 HTTP 请求头中的 Referer（来源页面地址）或 Origin。

**局限性**：某些浏览器可能会由于隐私设置隐藏 Referer，或者该字段可能被伪造（尽管在现代浏览器中较难）。


## 2. 同源策略(SOP)
### 2.1 基本概念
除非两张网页具有相同的“源”，否则 A 网页的脚本不能随意访问 B 网页的数据。  

1️⃣ **协议 (Protocol)**：如 http 与 https 不同。  
2️⃣ **域名 (Domain)**：如 google.com 与 baidu.com 不同。  
3️⃣ **端口 (Port)**：如 :80 与 :8080 不同。  

### 2.2 工作作用
####  ① DOM 访问
限制 A 网站的脚本读取或操作 B 网站的 DOM（例如，攻击者用 iframe 嵌一个伪造的银行登录框，如果没有 SOP，他就能拿到你输入的账号）。

####  ② 数据读取
限制 A 网站脚本读取 B 网站的 Cookie、LocalStorage 或 IndexedDB 数据。

####  ③ 网络请求
限制通过 XMLHttpRequest 或 Fetch API 发起的跨域请求（浏览器会拦截服务器返回的结果）。

### 2.3 安全场景
你刚刚登录了受信任网站 A，还没退出，又在一个新标签页打开了一个恶意网站 B。  
如果没有同源策略，B 页面上的 JavaScript 代码就可以：  
1️⃣ 直接读取你在 A 的登录 Cookie。  
2️⃣ 在你不知情的情况下，向 B 后台发送请求。  
3️⃣ 读取你的敏感信息。  

### 2.4 合法跨域
####  ① CORS (跨源资源共享)：
最正规的方法。服务器在响应头中加入 `Access-Control-Allow-Origin`，告诉浏览器：“我允许这个域名的访问”。
####  ② JSONP
利用 `<script>` 标签不受同源策略限制的漏洞（仅支持 GET 请求，现已逐渐过时）。
####  ③ 反向代理 (Nginx/Node.js)
让前端请求自己的服务器，再由服务器转发请求给真正的目标（服务器之间通信不受同源策略限制）。
