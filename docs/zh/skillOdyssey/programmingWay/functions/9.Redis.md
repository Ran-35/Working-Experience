# Redis 与 Redisson

## 1. Redis
### 1.1 基本概念 
Redis (Remote Dictionary Server) 是一个开源的内存数据结构存储系统，速度极快且简单。  

### 1.2 本质与核心特性 
* **本质**：非关系型键值数据库（NoSQL）  
* **核心特性**：基于内存；数据结构丰富；原子性。

💡Redis 性能极强的原因：  
* **全内存操作**：所有数据都在内存中，不涉及磁盘 I/O（除了持久化过程）。  
* **高效的数据结构**：每种数据类型都经过极致优化（如跳表、压缩列表等）。  
* **IO 多路复用模型**：Redis 使用单线程（核心网络处理部分）配合非阻塞 I/O，避免了多线程上下文切换带来的开销。  

### 1.3 五大数据结构
#### 1.3.1 String
最基础的类型，一个 Key 对应一个 Value。它是二进制安全的，意味着你可以存储图片、序列化后的对象或纯文本。

* **底层构造**：SDS (Simple Dynamic String)。相比 C 语言原生字符串，SDS 会记录长度（获取长度 $O(1)$），并预留空间（减少内存重分配）。  

* **常用命令**：  
| **命令**      | **复杂度** | **典型应用场景**                          |
| ----------- | ------- | ----------------------------------- |
| SET / GET   | O(1)    | 基础缓存（JSON对象、配置信息、Session）           |
| SETNX       | O(1)    | 简单的幂等性校验、轻量级分布式锁（Set if Not Exists） |
| INCR / DECR | O(1)    | 页面访问量(PV)、点赞数、验证码限流、全局序列号生成         |
| MGET / MSET | O(N)    | 批量获取商品详情、批量配置加载，减少网络 RTT            |
| GETRANGE    | O(N)    | 获取子字符串（类似 Java 的 substring）         |
| GETSET      | O(1)    | 原子性地更新值并返回旧值（重置计数器、更新配置快照）          |
| SETEX       | O(1)    | 设置值并指定过期时间，用于验证码或 Token             |

#### 1.3.2 Hash
一个键值对集合，类似于 Java 的 HashMap。它非常适合存储对象，因为它不需要像 String 那样序列化整个对象。

* **底层构造**：当数据量小时使用 `ziplist`（连续内存，极度省钱）；数据量大时转为 `hashtable`。 

* **常用命令**：    

| **命令**        | **复杂度** | **典型应用场景**                        |
| ------------- | ------- | --------------------------------- |
| HSET / HGET   | O(1)    | 存储对象（如用户信息：ID、姓名、年龄），支持单字段读写。     |
| HMSET / HMGET | O(N)    | 批量操作：一次性获取或设置用户的多个属性，减少网络往返。      |
| HSETNX        | O(1)    | 字段级幂等：仅当字段不存在时才设置，防止覆盖已有属性。       |
| HINCRBY       | O(1)    | 对象内计数：如购物车中商品数量加减、文章收藏数。          |
| HGETALL       | O(N)    | 获取完整对象：拉取对象的所有字段和值（慎用，N 较大时易阻塞）。  |
| HDEL          | O(N)    | 局部删除：删除对象中的某个属性（如删除用户收货地址）。       |
| HEXISTS       | O(1)    | 属性检查：判断对象中是否存在特定字段（如判断用户是否实名）。    |
| HLEN          | O(1)    | 统计规模：获取 Hash 中字段的数量（如统计购物车中商品数量）。 |

#### 1.3.3 List
双向链表结构，支持从左右两端推入或弹出元素。它保证了元素的插入顺序。

* **底层构造**：quicklist。是双向链表和 ziplist 的混合体，既保证了插入效率，又减少了空间碎片。 

* **常用命令**：  

| **命令**        | **复杂度** | **典型应用场景**                     |
| ------------- | ------- | ------------------------------ |
| LPUSH / RPUSH | O(1)    | 消息队列入队，最新社交动态/新闻发布（时间线）。       |
| LPOP / RPOP   | O(1)    | 任务处理出队，简单的生产者-消费者模型。           |
| LRANGE        | O(S+N)  | 分页查询（如获取前10条最新评论），获取热门动态列表。    |
| LINDEX        | O(N)    | 通过索引获取特定位置的元素（N为到达目标位置的距离）。    |
| LLEN          | O(1)    | 查看队列长度（如监控积压的任务数量）。            |
| LREM          | O(N)    | 删除特定元素（如用户取消点赞，从记录列表中移除用户ID）。  |
| LTRIM         | O(N)    | 固定窗口列表（如只保留最近100条系统日志，修剪掉旧数据）。 |
| BLPOP / BRPOP | O(1)    | 阻塞式消费（队列为空时进入等待，避免无效轮询，提高效率）。  |
| RPOPLPUSH     | O(1)    | 安全队列（取出任务并同时存入备份队列，防止数据丢失）。    |


#### 1.3.4 Set
无序、唯一的字符串集合。它可以自动去重，并支持求交集、并集、差集。

* **底层构造**：如果全是整数且数量少，用 `intset`，效率极高。否则，用 `hashtable`。 

* **常用命令**： 

| **命令**                  | **复杂度** | **典型应用场景**                           |
| ----------------------- | ------- | ------------------------------------ |
| SADD                    | O(N)    | 添加元素：抽奖名单、点赞过的用户 ID（自动去重）。           |
| SREM                    | O(N)    | 移除元素：取消关注、取消收藏。                      |
| SISMEMBER               | O(1)    | 判断是否存在：黑名单校验、是否已点赞、是否已签到。            |
| SMEMBERS                | O(N)    | 获取所有元素：展示好友列表、展示粉丝列表（数据量大时慎用）。       |
| SCARD                   | O(1)    | 获取集合大小：统计点赞数、统计参与人数。                 |
| SPOP                    | O(1)    | 随机弹出：随机抽奖、随机派发任务。                    |
| SRANDMEMBER             | O(1/N)  | 随机获取：不删除原数据的随机推荐、随机展示广告。             |
| SINTER / SUNION / SDIFF | O(N*M)  | 集合运算：共同好友（交集）、求职意向合并（并集）、可能认识的人（差集）。 |

#### 1.3.5 ZSet
Set 的基础上，给每个元素关联了一个 score（分数），使得集合中的元素可以按分数排序。

* **底层构造**：ziplist 或 skiplist（跳表）跳表是 Redis 的核心精华之一。它通过在链表之上增加多层索引，实现了类似二分查找的效率（平均复杂度 $O(\log N)$）。 

* **常用命令**：   

| **命令**             | **复杂度**       | **典型应用场景**                          |
| ------------------ | ------------- | ----------------------------------- |
| ZADD               | O(log(N))     | 添加成员或更新分数：排行榜实时更新、带权重的任务队列。         |
| ZRANGE / ZREVRANGE | O(log(N) + M) | 获取指定排名区间内的成员：热点新闻 Top 10、排行榜前 50 名。 |
| ZSCORE             | O(1)          | 查看某个特定成员的分数：查询某用户的具体积分、商品的销量。       |
| ZCARD              | O(1)          | 获取集合内的成员总数：统计参与投票的总人数。              |
| ZREM               | O(log(N))     | 移除一个或多个成员：用户取消关注、商品下架。              |
| ZINCRBY            | O(log(N))     | 增加指定成员的分数：每点击一次文章，对应的热度分 +1。        |
| ZRANK / ZREVRANK   | O(log(N))     | 获取成员的排名（从 0 开始）：查询用户当前的全球排名。        |
| ZRANGEBYSCORE      | O(log(N) + M) | 根据分数区间获取成员：筛选价格在 100-500 元之间的商品。    |


### 1.4 数据持久化
#### 1.4.1 RDB (Redis Database) - 快照模式
RDB 相当于给内存数据“拍照片”。它在指定的时间间隔内，将内存中的全量数据生成一个二进制压缩文件（默认名为 dump.rdb）保存到硬盘。

##### ① 工作原理
1️⃣ **Fork 子进程**：Redis 调用系统的 fork() 函数创建一个子进程。  
2️⃣ **写时复制 (COW)**：父进程继续处理客户端写操作，而子进程将内存中的数据写入临时 RDB 文件。如果父进程修改了某个数据页，操作系统会为该页创建副本，确保子进程看到的是 fork 瞬间的数据镜像。  
3️⃣ **替换文件**：子进程写完后，用新的 RDB 文件替换掉旧的 dump.rdb。  

##### ② 优缺点     

| **优点**                                      | **缺点**                           |
| ------------------------------------------- | -------------------------------- |
| **恢复速度快**：二进制文件直接加载，远快于 AOF 命令重放。               | **数据丢失风险**：两次快照之间的数据如果宕机将会丢失。        |
| **性能影响小**：BGSAVE 由子进程完成，不阻塞主进程（仅在 fork 时有瞬时抖动）。 | **资源消耗**：数据量巨大时，fork 子进程可能导致服务器卡顿。   |
| **文件紧凑**：适合用于备份和全量数据迁移。                         | **版本兼容性**：不同版本的 Redis RDB 格式可能不完全兼容。 |

##### ③ 触发方式

| **触发方式** | **命令/配置**                | **行为特点**                               |
| -------- | ------------------------ | -------------------------------------- |
| 手动同步     | SAVE                     | 阻塞 Redis 服务器，直到 RDB 文件创建完毕，线上环境禁忌使用。   |
| 手动异步     | BGSAVE                   | 非阻塞。Redis 会 fork 出一个子进程负责写入，服务器继续处理请求。 |
| 自动触发     | save `<seconds>` `<changes>` | 在指定时间内发生指定次数的修改，Redis 自动执行 BGSAVE。     |
| 关闭服务     | SHUTDOWN                 | 如果没有开启 AOF，Redis 在正常关闭前会执行一次 SAVE。     |

自动触发时，需要在redis.conf中配置：
```txt
# 自动触发规则：900秒内至少1个key修改，或300秒内10个修改
save 900 1
save 300 10
save 60 10000

# RDB 文件保存的名称
dbfilename dump.rdb

# RDB 文件保存的目录
dir ./

# 后台保存出错时，是否停止写操作（保护数据一致性）
stop-writes-on-bgsave-error yes

# 是否对 RDB 文件进行压缩（建议开启，节省空间但耗费CPU）
rdbcompression yes
```

#### 1.4.1 AOF (Append Only File) - 日志模式
AOF 像是一个“记事本”。它记录 Redis 执行的所有写操作命令，以追加的方式写入文件（默认 appendonly.aof）。

##### ① 三种策略  

| **策略选项**      | **同步频率**     | **优点**            | **缺点**     |
| ------------- | ------------ | ----------------- | ---------- |
| always        | 每个写命令执行完立即同步 | 数据最安全，理论上不丢数据     | 性能极差，磁盘压力大 |
| everysec (推荐) | 每秒执行一次同步     | 性能极好，宕机最多丢失 1 秒数据 | 极低概率的数据丢失  |
| no            | 由操作系统控制同步时机  | 性能最高              | 宕机丢失数据量不可控 |

##### ② 重写机制  
随着运行时间增长，AOF 文件会变得非常臃肿（例如：对同一个 Key 自增 100 次，AOF 会记录 100 条命令）。 重写会分析内存中的当前数据，将其转化为最少的命令集合。

* **原理**：Redis 会 fork 一个子进程，读取当前内存快照并生成新 AOF，最后替换旧文件。这个过程是增量式的，不会阻塞主进程。

* **触发方式**：

1.手动：执行 BGREWRITEAOF 命令。  
2.自动：配置 auto-aof-rewrite-percentage 100（当前大小比上次重写后增长一倍时触发）。  

##### ③ 使用方法
默认是关闭，需要在redis.conf中手动开启
```txt
# 1. 开启 AOF (前提条件)
appendonly yes

# 2. 设置触发重写的百分比
# 表示当前 AOF 文件大小超过上一次重写后大小的百分之多少时，触发重写。
# 100 表示文件大了一倍时触发。
auto-aof-rewrite-percentage 100

# 3. 设置触发重写的最小数值
# 为了防止在文件还很小时（例如只有几兆）频繁触发重写。
# 只有 AOF 文件大于 64mb 时，上面的百分比规则才会生效。
auto-aof-rewrite-min-size 64mb

# 4. 重写期间是否同步 AOF (建议选 no)
# 如果选 yes，在高并发写操作时可能会因为子进程的磁盘 IO 压力导致主进程阻塞。
# 选 no 则在重写期间不进行 fsync，性能更好，但安全性略低。
no-appendfsync-on-rewrite no
```

#### 1.4.1 混合持久化 (Mixed Persistence)
##### ① 工作原理
在 AOF 重写时，先将当前内存数据以 RDB 的二进制格式写入 AOF 文件的开头，再将重写期间产生的增量命令以 AOF 格式追加到文件末尾。  

当手动执行 BGREWRITEAOF 或达到 auto-aof-rewrite-percentage 阈值时：  

1️⃣ Fork 子进程：创建一个子进程来处理重写。  
2️⃣ 写入 RDB 内容：子进程将当前内存中的数据转换为 RDB 格式，写入新的 AOF 文件头部。  
3️⃣ 追加 AOF 内容：在重写期间，主进程处理的新写命令会被记录在内存缓冲区中。当 RDB 写入完成后，这些增量命令以 AOF 格式追加到新文件的末尾。  
4️⃣ 替换文件：用这个“前半部分是 RDB，后半部分是 AOF”的新文件替换旧的 AOF 文件。  

##### ② 优缺点

| **特性** | **混合持久化的优势**                   | **潜在代价**                             |
| ------ | ------------------------------ | ------------------------------------ |
| 恢复速度   | 极快。加载前半部分的 RDB 远快于逐条执行 AOF 命令。 | —                                    |
| 数据安全性  | 高。结合了 AOF 的增量记录，数据丢失风险小。       | —                                    |
| 文件大小   | 较小。RDB 格式比纯 AOF 文本格式更紧凑。       | —                                    |
| 兼容性    | —                              | 向下兼容性差。Redis 4.0 之前的版本无法识别这种混合格式。    |
| 可读性    | —                              | AOF 文件的头部变成了二进制，无法像以前那样直接用 `cat` 查看。 |

##### ③ 使用方式
在redis.conf配置文件中：
```txt
# 必须先开启 AOF
appendonly yes

# 开启混合持久化
aof-use-rdb-preamble yes
```

或者：直接使用命令行
```txt
CONFIG SET appendonly yes
CONFIG SET aof-use-rdb-preamble yes
```

### 1.5 主从复制
Redis 实现高可用和高性能的基石。它允许一个 Redis 服务器（Master）的数据同步到任意数量的从服务器（Slave/Replica）。

#### 1.5.1 核心原理
✅ 三个阶段：`建立连接`--> `全量复制` --> `增量复制`

##### 阶段一：建立连接
1️⃣ 从节点执行 `replicaof <master-ip> <master-port>` 命令。  
2️⃣ 从节点保存主节点信息，并与主节点建立 Socket 连接。  
3️⃣ 从节点发送 PING 命令，建立心跳机制。  

##### 阶段二：全量复制 (Full Resync)
这是最耗时的阶段，通常发生在从节点第一次连接主节点时。

1️⃣ 主节点执行 bgsave 生成 RDB 文件，期间产生的写命令缓存到 replication buffer 中。  
2️⃣ 主节点将 RDB 文件发送给从节点。  
3️⃣ 从节点清空旧数据，加载 RDB 文件。  
4️⃣ 主节点将缓存的写命令发给从节点执行。  

##### 阶段三：增量复制 (Partial Resync)
当从节点短时间断开重连时，不再进行昂贵的全量复制，而是进行增量补发。

1️⃣ 复制偏移量 (Offset)：主从双方都维护一个偏移量，记录同步进度。  
2️⃣ 复制积压缓冲区 (Backlog)：主节点内存中维护一个固定大小的 FIFO 队列。  
3️⃣ 判定逻辑：如果从节点断开期间丢失的数据还在缓冲区内，则进行增量复制；否则退化为全量复制。


#### 1.5.2 三种模式
| 模式               | 特点                               | 适用场景                   |
| ---------------- | -------------------------------- | ---------------------- |
| 一主一从             | 最基础的主从模式，1个主节点和1个从节点，数据备份        | 数据备份、容错、简单的读写分离        |
| 一主多从             | 1个主节点和多个从节点，多个从节点共享同一个主节点的读操作    | 读压力极大的场景（读写分离），提高读取性能  |
| 树状主从 (Cascading) | 从节点也可以作为其他从节点的“主”，减轻主节点的同步 IO 压力 | 当主节点带宽受到限制，防止同步操作带来的瓶颈 |

#### 1.5.3 工作用途
* **读写分离**：
(1)主节点负责写操作，从节点负责读操作。  
(2)通过横向增加从节点，可以线性提升系统的只读并发量。  

* **数据冗余**：主从复制实现了数据的热备份，是 RDB/AOF 之外的另一种安全保障。   
* **高可用基础**：它是 Sentinel (哨兵) 和 Cluster (集群) 的物理基础。如果没有主从，故障转移就无从谈起。  

#### 1.5.4 注意事项
* **主从数据不一致**：由于 Redis 复制是异步的，主节点返回“写成功”时，数据可能还没到从节点。对一致性要求极高的业务（如余额），读请求应强制走主节点。

* **读到过期数据**：在 Redis 3.2 之前，从节点不会主动删除过期 Key，可能读到过期数据。现代版本已修复，从节点会通过逻辑判断该 Key 是否已过期。

* **复制风暴**：如果多个从节点同时启动并向主节点请求全量复制，主节点的带宽和磁盘 IO 会瞬间爆满。建议： 采用树状结构或分批启动从节点。

* **避免全量复制**：调大 repl-backlog-size（默认 1MB），防止因网络小波动导致从节点偏移量溢出缓冲区，从而引发不必要的全量同步。

#### 1.5.5 使用步骤
若要在项目中开启从节点读数据：
```yml
spring:
  data:
    redis:
      # 读写分离配置（需配合哨兵或集群模式效果更佳）
      lettuce:
        extension:
          read-from: replica # 优先读取从节点
```

### 1.6 哨兵机制
Redis 哨兵（Sentinel） 是 Redis 的高可用解决方案。在主节点宕机时，能够自动完成故障发现、主从切换和通知客户端。

#### 1.6.1 核心功能
* **监控（Monitoring）**：持续检查主从节点是否运作正常。

* **通知（Notification）**：当某个 Redis 节点出现问题时，哨兵能通过 API 通知管理员或其他应用程序。

* **自动故障转移（Automatic Failover）**：如果主节点挂了，哨兵会选举一个从节点晋升为新主节点，并让其他从节点指向新主节点。

* **配置中心（Configuration Provider）**：客户端（如你的 Java 脚手架）初始化时连接的是哨兵，哨兵会告知当前谁是主节点。

#### 1.6.1 工作原理
##### ① 判断掉线
哨兵判断一个主节点掉线需要经过两步：

1️⃣ **主观下线（Subjective Down, SDOWN）**： 单个哨兵发现主节点在 is-master-down-after-milliseconds 时间内没回心跳，它就认为该主节点“挂了”。  
2️⃣ **客观下线（Objective Down, ODOWN）**： 当超过法定人数的哨兵都认为该主节点挂了，它们会互相交流并达成共识。此时，才会触发真正的切换流程。
##### ② 切换节点
1️⃣ **选出领头哨兵（Leader）**。  
2️⃣ **从节点筛选**：在剩余从节点中挑选。  
(1)优先级：先看 replica-priority（手动配置的权重）。  
(2)同步进度：选偏移量（Offset）最大的，即数据最全的。  
(3)运行 ID：如果以上都一样，选 RunID 最小的。  
3️⃣ **身份切换**：  
(1)发送 SLAVEOF NO ONE 给选中的从节点，让其变身 Master。  
(2)向其他从节点发送命令，让它们去追随新的 Master。  
(3)即使原主节点重启，哨兵也会强制让它变成新主节点的从节点。  

#### 1.6.2 使用方法
```yml
spring:
  data:
    redis:
      sentinel:
        master: mymaster          # 哨兵配置文件中指定的 Master 名称
        nodes:                    # 哨兵集群地址
          - 192.168.1.10:26379
          - 192.168.1.11:26379
          - 192.168.1.12:26379
      lettuce:
        extension:
          read-from: replica      # 依然支持读写分离，优先读从节点
```

### 1.7 Redis集群
Redis 集群（Redis Cluster）是 Redis 提供的分布式数据库方案，它通过分片（Sharding）来保存数据，从而解决了单机内存、并发性能的瓶颈，并实现了真正的高可用。

#### 1.7.1 核心原理
哈希槽 (Hash Slot) 是实现数据分片（Sharding）的核心机制。它解决了在分布式环境下，数据该“存放在哪台机器”以及“如何平滑扩容”的问题。

* **槽的数量**：集群固定拥有 16384 ($2^{14}$) 个哈希槽。  
* **分配方式**：节点 A 负责 0 - 5460 号槽；节点 B 负责 5461 - 10922 号槽；节点 C 负责 10923 - 16383 号槽。  
* **寻址公式**：HASH_SLOT = CRC16(key) mod 16384。  

#### 1.7.2 主从复制与故障转移
每个 Master 节点通常会配置 1 到多个 Slave 节点。

* **自动故障发现**：节点之间通过 Gossip 协议 互相交换状态信息。

* **故障转移 (Failover)**：
(1)当节点 A 宕机，其他 Master 节点会检测到其下线。  
(2)从节点 A1 会被选举并晋升为新的 Master。  
(3)集群自动更新哈希槽映射。  
* **集群不可用判定**：如果某个哈希槽对应的 Master 和所有 Slave 都挂了，或者超过半数的 Master 挂了，整个集群将进入 fail 状态。

#### 1.7.3 关键特性
##### ① 智能重定向 (MOVED & ASK)
当你向节点 A 发送一个属于节点 B 的 Key 时，节点 A 会返回一个 MOVED 错误，告诉客户端正确的 IP 和端口。  
⚠️注意：在 Java 中，你的 JedisCluster 或 Lettuce (Spring Boot 默认) 已经自动处理了这种重定向，开发者无感。

##### ② 多键操作限制 (Multi-Key)
Redis 集群不支持跨节点的批量操作（如 MSET、SUNION），因为这些 Key 可能分布在不同的槽位。

💡解决方法：使用 Hash Tag。例如设置 Key 为 {user:100}:order 和 {user:100}:profile。大括号内的内容相同，则它们一定会被分配到同一个槽位。


### 1.8 三大并发问题
#### 1.8.1 缓存雪崩
* **问题**：大量 Key 在同一时间失效。

* **解决**：设置随机过期时间，或使用分布式锁。

#### 1.8.1 缓存击穿
* **问题**：某个“热点” Key 突然失效，海量请求直冲数据库。

* **解决**：设置热点数据永不过期。

#### 1.8.1 缓存穿透
* **问题**：请求的数据在 Redis 和数据库中都不存在（黑客攻击）。

* **解决**：布隆过滤器 (Bloom Filter)。

## 2. Redisson
### 2.1 基本概念 
在 Redis 基础上实现的 Java 驻内存数据网格（In-Memory Data Grid）。它不仅提供了基本的 Redis 操作，更重要的是它实现了许多复杂的分布式服务。。  

### 2.2 作用 
原生的 Redis 客户端（如 Jedis 或 Lettuce）更偏向于“命令式”，你需要自己去写逻辑实现分布式锁、限流等功能。而 Redisson 实现了大量的 JUC (java.util.concurrent) 接口，让你像在本地操作集合一样操作分布式数据。  

### 2.3 核心功能
#### 2.3.1 分布式锁（RLock）
* **看门狗机制（Watchdog）**：自动给锁续期，防止业务没执行完锁就过期了。

* **公平锁/红锁（RedLock）**：解决集群环境下的锁安全问题。
#### 2.3.2 分布式集合
* **RMap**：可以像使用 HashMap 一样使用 RMap，数据会自动同步到 Redis。
