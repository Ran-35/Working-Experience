# Locking Mechanisms

✅**Locks**: A commonly used synchronization mechanism used to ensure that multiple threads can access shared resources in a mutually exclusive manner, preventing inconsistencies caused by multiple threads accessing or modifying shared resources simultaneously.

✅**Optimistic Locking**: Assumes the best-case scenario, believing that no problems will occur each time the shared resource is accessed. Threads can execute continuously without locking or waiting, only verifying whether the corresponding resource (i.e., data) has been modified by other threads when committing changes (specific methods can use version number mechanisms or CAS algorithms).

✅**Pessimistic Locking**: Always assumes the worst-case scenario, believing that problems will occur each time the shared resource is accessed (e.g., shared data is modified). Therefore, a lock is acquired every time the resource is acquired, blocking other threads from acquiring the resource until the lock is released by the previous holder. In other words, the shared resource is only available to one thread at a time; other threads are blocked, and the resource is then released to other threads after use.

| **Dimension**      | **Pessimistic Locking**                                                        | **Optimistic Locking**                                                            |
| ------------------ | ------------------------------------------------------------------------------ | --------------------------------------------------------------------------------- |
| **Core Idea**      | "There are always malicious people trying to harm me" — lock before operation. | "Everyone is good" — check at the time of update.                                 |
| **Implementation** | `synchronized`, `ReentrantLock`, database `select for update`                  | `CAS` mechanism, version number mechanism                                         |
| **Overhead**       | Involves thread blocking and context switching, leading to high overhead.      | Does not block threads, but may cause high CPU consumption under high contention. |
| **Use Case**       | Many writes and few reads, high competition, long synchronization blocks.      | Many reads and few writes, low competition.                                       |


## 1. volatile

The lightest synchronization mechanism provided by the Java Virtual Machine. Unlike `synchronized`, it does not provide mutual exclusion (it will not cause thread blocking) and is mainly used to solve visibility and ordering problems between multiple threads.

### 1.1 Guaranteeing Visibility

In a multithreaded environment, each thread has its own working memory (cache). When one thread modifies a regular variable, other threads may not be able to see it immediately.
| **Type**              | **Description** |
| --------------------- | ----------------|
| **Normal Variable**   | After modification, it may still be in the cache and not immediately written back to the main memory.|
| **volatile Variable** | Once modified, the JVM immediately flushes it to the main memory and invalidates the copy in other threads' working memory (disables CPU caching). Threads must retrieve the latest value from the main memory when reading. |


### 1.2 Ensuring Ordering 

To optimize performance, compilers and processors reorder instructions.
| **Type**                           | **Description**|
| ---------------------------------- | -------------- |
| **Prevent Instruction Reordering** | `volatile` ensures the execution order of instructions by inserting a memory barrier.          |
| **Classic Case**                   | In the Singleton pattern, the DCL (Double-Checked Locking) must use `volatile` on the instance variable to prevent the reference from being assigned to the variable before the object is fully initialized (i.e., before the constructor completes). |


### 1.3 No Atomicity Guarantee

volatile only guarantees the atomicity of a single read/write operation (e.g., read/write of long/double), but not the atomicity of compound operations (e.g., i++).

**Example**
```java
// Reason: Thread A reads count = 5, and then Thread B also reads count = 5. A increments by 1 and writes back 6, then B writes back 6 later. 
// In reality, only one increment was applied due to the race condition.
public class VolatileTest {
    public volatile int count = 0;

    public void add() {
        count++; // This is a compound operation: read -> increment -> write
    }

    public static void main(String[] args) throws InterruptedException {
        VolatileTest test = new VolatileTest();
        // Start 10 threads, each performing 1000 increments
        for (int i = 0; i < 10; i++) {
            new Thread(() -> {
                for (int j = 0; j < 1000; j++) test.add();
            }).start();
        }
        Thread.sleep(2000);
        System.out.println(test.count); // The result is usually less than 10000
    }
}

```
### 1.4 Use Cases

1. Status Flags: For example, `volatile boolean stop = false;` is used to stop a thread.
2. Double-Checked Locking (DCL): Prevents null pointer exceptions caused by instruction reordering in the Singleton pattern.
3. Read-heavy, Write-light: Only one thread modifies a variable, while other threads read it.

## 2. Pessimistic Locking - `Synchronized` (Built-in Lock)

The most basic locking mechanism: The `Synchronized` keyword is a built-in atomic lock provided by Java. Its core idea is that any object can act as a lock.

### 2.1 Underlying Principles

📌 The core of `synchronized` is the Monitor (monitor lock). Each Java object is associated with a Monitor object internally within the JVM.

👉 **monitorenter**: Each object has a lock counter. When the counter is 0, a thread enters and sets it to 1, becoming the owner of the Monitor. If it re-enters, the counter is incremented.

👉 **monitorexit**: The thread releases the lock, and the counter is decremented by 1. When it reaches 0, the lock is completely released.

⚠️ Key point: `synchronized` is reentrant. It tracks how many times the current thread has acquired the lock using the recursions counter inside the Monitor.

### 2.2 Lock Elevation Process

✅ To balance "safety under high concurrency" and "high performance under single-threaded conditions," the lock undergoes an escalation process from low to high:

#### 2.2.1 First Stage: Biased Locking

📌 **Principle**: In most cases, the lock not only has no contention but is also always acquired by the same thread. Biased locking records the thread's ID in the Mark Word.

👉 **Operation**: When the same thread enters later, only the thread ID needs to be compared; no synchronization operation is required (no CAS, no memory barriers).

👉 **Triggering Elevation**: When a second thread attempts to compete for the lock, the biased lock becomes ineffective.

#### 2.2.2 Second Stage: Lightweight Locking

📌 **Principle**: When contention occurs, but is not intense (threads execute alternately), the lock is upgraded to a lightweight lock.

👉 **Operation**: The JVM creates a "Lock Record" in the current thread's stack frame and attempts to replace the Mark Word in the object header with a pointer to the lock record using CAS.

👉 **Spin Optimization**: If CAS fails, the thread does not immediately suspend but spins (an empty loop), waiting for the thread holding the lock to release it.


#### 2.2.3 Third Stage: Heavyweight Locking

📌 **Principle**: If contention is very intense, and the thread spins a certain number of times (or multiple threads are queuing), the lock is escalated to a heavyweight lock.

👉 **Operation**: The Mark Word points to the Monitor. Threads that fail to acquire the lock will enter a blocked state and be handed over to the operating system for scheduling.

👉 **Overhead**: Involves context switching from user mode to kernel mode, resulting in the highest performance penalty.

#### 2.2.4 Design Philosophy

🏷️ Biased Locking: To allow a single thread to execute a synchronized block as quickly as if no lock were acquired.

🏷️ Lightweight Locking: To avoid the system call overhead caused by thread suspension during short-term contention.

🏷️ Heavyweight Locking: To save CPU resources (avoiding unnecessary spinning) by suspending threads during long-term, intense contention.

### 2.3 Several Usage Examples

#### 2.3.1 Instance Locking (Locking Object Instances)

📌 **Function**: Locks the current `this` object. If two threads access the same synchronized method of the same object, contention will occur; if they access synchronized methods of different objects, there will be no contention. 

```java
public class SyncExample {
    // 1. Synchronized instance method
    public synchronized void method1() {
        // Critical section code
    }

    // 2. Synchronized block (specifying the lock object)
    public void method2() {
        synchronized (this) {
            // The effect is the same as method1
        }
    }
}

```

```java
public class MyClass {
    private void increment() {}
    private synchronized void decrement() {}
}
```

| **Thread A**  | **Thread B**  | **Result**     | **Reason**   |
| ------------- | ------------- | -------------- | ------------ |
| `increment()` | `increment()` | Can execute    | `increment()` is not synchronized, so no lock is applied.                                     |
| `increment()` | `decrement()` | Can execute    | Locks are applied to different methods, so they do not conflict.                              |
| `decrement()` | `decrement()` | Cannot execute | Both methods are synchronized and locked, so one must wait for the other to release the lock. |


#### 2.3.2 Class Lock (Locking the Class Object)

📌 **Purpose**: Locks the `Class` template of the class. No matter how many instances are created, there is only one class lock for this class.

```java
public class SyncExample {
    // 1. Synchronized static method
    public static synchronized void staticMethod() {
        // Global unique lock
    }

    // 2. Synchronized block (lock on a specified class)
    public void method3() {
        synchronized (SyncExample.class) {
            // The effect is the same as the static method
        }
    }
}

```
```java
public class MyClass {
    private static void increment() {}
    private static synchronized void decrement1() {}
    private static synchronized void decrement2() {}
}
```
| **Thread A**   | **Thread B**   | **Result**     | **Reason**     |
| -------------- | -------------- | -------------- | -------------- |
| `increment()`  | `increment()`  | Can execute    | `increment()` is not synchronized, so no lock is applied.                            |
| `increment()`  | `increment1()` | Cannot execute | The lock is on the class, so one thread must wait for the other to release the lock. |
| `decrement1()` | `decrement1()` | Cannot execute | The lock is on the class, so one thread must wait for the other to release the lock. |
| `decrement1()` | `decrement2()` | Cannot execute | The lock is on the class, so one thread must wait for the other to release the lock. |


### 2.4 Difference between synchronized and volatile
| **Feature**     | **volatile**  | **synchronized**  |
| --------------- | ------------- | ----------------- |
| **Atomicity**   | ❌ Only guarantees single read/write | ✅ Guaranteed (via mutex lock) |
| **Visibility**  | ✅ | ✅                                                     |
| **Ordering**    | ✅ (Prevents reordering)    | ✅ (Guaranteed by mutex semantics)|
| **Performance** | 🚀 Very high (non-blocking) | 🐢 Relatively low (may involve lock upgrade/blocking) |
| **Usage**       | Variable                     | Methods, code blocks               |


## 3. Pessimistic Locking - ReentrantLock (Reentrant Lock / Explicit Lock)

Introduced in Java 5, ReentrantLock offers more flexibility and power than `synchronized`, allowing programmers to explicitly control lock acquisition and release. It also provides additional features such as attempted lock acquisition, timeout lock acquisition, and interruptible locks.

Underlying Principle: The core of ReentrantLock is AQS (AbstractQueuedSynchronizer). It's a framework for building locks and synchronizers.

### 3.1 Core Features

#### 3.1.1 Explicit Creation, Locking, and Release

**Creation**: `ReentrantLock lock = new ReentrantLock();`  
**Acquisition**: `lock.lock()`  
**Release**: `lock.unlock()`  

```java
public class MyClass {
    private final ReentrantLock lock = new ReentrantLock();

    public void test() {
        lock.lock();
        try {
            // Access shared resources
        } finally {
            lock.unlock();
        }
    }
}
```
#### 3.1.2 Reentrancy

A single thread can acquire the same lock multiple times. If a thread has already acquired the lock, it can still acquire the lock again without deadlock.

```java
public class MyClass {
    private final ReentrantLock lock = new ReentrantLock();

    public void methodA() {
        lock.lock();
        try {
            methodB(); // Call methodB inside methodA
        } finally {
            lock.unlock();
        }
    }

    public void methodB() {
        lock.lock();  // The current thread acquires the lock again
        try {
            System.out.println("Executing methodB...");
        } finally {
            lock.unlock();
        }
    }
}
```

#### 3.1.3 Timeout Mechanism

`ReentrantLock` provides the `tryLock()` method, which does not block the current thread. If the lock is unavailable, it immediately returns `false`, without waiting indefinitely.

**Use Cases**: Scenarios where blocking needs to be avoided.

* `tryLock()`: Attempts to acquire the lock. If the lock is unavailable, it immediately returns `false`.
* `tryLock(long timeout, TimeUnit unit)`: Attempts to acquire the lock. If the lock is unavailable, it waits for the specified time. If the lock cannot be acquired within the specified time, it returns `false`.

```java
public class MyClass {
    private final ReentrantLock lock = new ReentrantLock();

    public void test() {
        if (lock.tryLock()) {
            try {
                // Access shared resources
            } finally {
                lock.unlock();
            }
        } else {
            // If the lock is unavailable, perform other operations.
        }
    }
}
```

#### 3.1.4 Responding to Interruptions

Interruptible locks allow a thread to be interrupted while waiting for a lock, throwing an exception.

**Use Cases**: In high-concurrency or long-term lock waiting scenarios, threads need to be externally interrupted while waiting for a lock.

* `lockInterruptibly()`: Allows a thread to be interrupted while waiting for a lock. If the thread is interrupted before acquiring the lock, it throws an `InterruptedException`.

```java
public class MyClass {
    private final ReentrantLock lock = new ReentrantLock();

    public void test() {
        try {
            lock.lockInterruptibly();
        } catch (InterruptedException e) {
            // Handling interrupt exceptions
        } finally {
            lock.unlock();
        }
    }
}
```

#### 3.1.5 Fair Locks vs. Unfair Locks

By default, `ReentrantLock` is an unfair lock, meaning the order in which threads acquire the lock is arbitrary; the thread that executes first acquires the lock first.

* **Fair Locks**: Ensure threads acquire the lock in the order they request it, thus avoiding the "starvation" problem, but performance may be worse.  

* **Unfair Locks**: The order in which threads acquire the lock is arbitrary; the thread that executes first acquires the lock first.

```java
ReentrantLock fairLock = new ReentrantLock();     // The default is a non-fair lock.
ReentrantLock fairLock = new ReentrantLock(true); // true indicates a fair lock.
```
### 3.2 Lock Upgrade

1️⃣ **Direct Attempt**: Upon entering a thread, it first attempts to change the state from 0 to 1 using CAS. If successful, it directly acquires the lock.  
2️⃣ **Reentrancy Check**: If this fails, it checks if the current thread is already the lock holder. If so, it increments the state and acquires the lock successfully.  
3️⃣ **Enqueue and Suspend**: If the above fails, the thread is placed at the tail of the AQS queue and suspended (entering a waiting state) using LockSupport.park().  
4️⃣ **Blocking Spin**: Threads in the queue (usually the head thread) continuously attempt to acquire the lock until they succeed.

### 3.3 Use Cases

* **High Concurrency**: When multiple threads compete for a lock, `ReentrantLock` provides more flexible control than `synchronized`, such as interruptible locks and timed locks.

* **Complex Synchronization Needs**: When multiple locking mechanisms are required (such as fairness, try-and-play locks, interruptible locks, etc.), `ReentrantLock` provides more options.

* **Deadlock Prevention**: Deadlocks can be avoided through lock order control and methods such as `tryLock()`.


### 3.4 Comparison of ReentrantLock and Synchronized
| **Feature**             | **Synchronized**                              | **ReentrantLock**                             |
| ----------------------- | --------------------------------------------- | --------------------------------------------- |
| **Implementation**      | JVM keyword (implemented in C++)              | JDK API (implemented in Java)                 |
| **Flexibility**         | Automatic lock/unlock, less flexible          | Manual control, extremely flexible            |
| **Fairness**            | Only supports non-fair locking                | Supports both fair and non-fair locking       |
| **Interruptibility**    | Not interruptible                             | Interruptible                                 |
| **Condition Variables** | Only one (wait/notify)                        | Supports multiple `Condition` objects         |
| **Performance**         | After Java 6 optimization, on par with `Lock` | More stable performance under high contention |


## 4. Pessimistic Locking - ReadWriteLock

✅ Concept: A lock interface provided by Java that improves performance by dividing the lock into `readLock` and `writeLock`.

Design Goal: Allows multiple threads to concurrently read data. However, when writing data, other threads cannot read or write.

📅 Underlying Principle: Based on AQS, but AQS has only one state variable. ReadWriteLock cleverly "divides" it in two:

* High 16 bits: Represents the read lock state (the number of times the read lock has been held; if it's a re-entry, it's incremented).

* Low 16 bits: Represents the write lock state (the number of times the write lock has been re-entered).

* Write Lock Acquisition: When both the low 16 bits and high 16 bits of the state are 0, the write lock can be acquired.

* Read lock acquisition: As long as the lower 16 bits (write lock) are 0, regardless of the value of the higher 16 bits, a thread can acquire the read lock by incrementing the value of the higher 16 bits through CAS.

### 4.1 Core Rules

✅ The core logic of ReadWriteLock can be summarized as: "Read-read shared, read-write mutually exclusive, write-write mutually exclusive".

| **Lock State** | **Read Lock**               | **Write Lock** |
| -------------- | --------------------------- | -------------- |
| **Read Lock**  | ✅ Allows (Concurrent reads) | ❌ Blocks       |
| **Write Lock** | ❌ Blocks                    | ❌ Blocks       |



### 4.2 Read Locks, Write Locks, and Creating Read-Write Locks

* `readLock()`: Read lock.

(1) A read lock is a shared lock; multiple threads can acquire the same read lock simultaneously, as long as no thread holds a write lock.

(2) Acquiring a read lock is non-exclusive; multiple threads can read data simultaneously, thus improving performance.

(3) A read lock cannot coexist with a write lock. That is, if a thread holds a read lock, other threads cannot acquire a write lock.

* `writeLock()`: Write lock.

(1) A write lock is an exclusive lock; it is exclusive. When one thread holds a write lock, other threads cannot acquire either a write lock or a read lock.

(2) A write lock will block all read locks and other write locks until the write operation is complete.

(3) A write lock has higher priority because it needs to guarantee data consistency.

```java
import java.util.concurrent.locks.ReentrantReadWriteLock;

public class CacheData {
    private Object data;
    // Create a read-write lock
    private final ReentrantReadWriteLock rwLock = new ReentrantReadWriteLock();

    // Read operation
    public void read() {
        rwLock.readLock().lock(); // Acquire the read lock
        try {
            System.out.println(Thread.currentThread().getName() + " is reading data: " + data);
        } finally {
            rwLock.readLock().unlock(); // Release the read lock
        }
    }

    // Write operation
    public void write(Object newData) {
        rwLock.writeLock().lock(); // Acquire the write lock
        try {
            System.out.println(Thread.currentThread().getName() + " is writing data...");
            this.data = newData;
        } finally {
            rwLock.writeLock().unlock(); // Release the write lock
        }
    }
}

```
### 4.3 Lock Downgrading

⭐ReentrantReadWriteLock supports lock downgrading, i.e.: acquire a write lock -> acquire a read lock -> release the write lock. This allows a thread to switch from write mode to read mode without releasing the lock, ensuring data visibility.

⚠️Note: Lock upgrading is not supported (directly changing from a read lock to a write lock will result in a deadlock).

### 4.4 Comparison between ReentrantReadWriteLock and ReentrantLock
| **Dimension**   | **ReentrantLock**                                     | **ReentrantReadWriteLock**                                         |
| --------------- | ----------------------------------------------------- | ------------------------------------------------------------------ |
| **Concurrency** | Complete mutual exclusion                             | Allows concurrent read operations                                  |
| **Use Case**    | Many write operations, or a balanced read-write ratio | More reads than writes (e.g., cache lookup, configuration reading) |
| **Overhead**    | Low                                                   | Slightly higher (due to maintaining two locks)                     |


## 5. Optimistic Locking - Version Number Mechanism

✅ Core Logic: Read the data and retrieve the version number; update by comparing the version number.

This is the most common method at the database level. Add a `version` field to the table.

1️⃣ Initial State: The database record contains a data field and a `version` field (usually starting from 0 or 1).  
2️⃣ Read Phase: Thread A reads the data and also reads the current `version` = 1.  
3️⃣ Logic Processing: Thread A modifies the data in memory.  
4️⃣ Write Phase: Thread A prepares to commit the update, at which point it executes conditional SQL.  
4.1 Check: The database checks if the `version` of the current record is still 1.  
4.2 Success: If it is still 1, it means no one has modified it during this period. Execute the update and change `version` to 2.  
4.3 Failure: If `version` has already become 2 (previously modified by someone else), the update fails.

### Version Number Mechanism vs. Timestamp Mechanism (5.1)
| **Method**         | **Advantages**         | **Disadvantages**                 |
| ------------------ | ---------------------- | --------------------------------- |
| **Version Number** | Simple, precise, not affected by system time.              | Requires maintaining an additional field.                                                                            |
| **Timestamp**      | No extra logic needed, the table typically already has `update_time`. | In high concurrency (millisecond precision), if two requests arrive at the same time, the timestamp may be the same. |


⚠️ Note: Due to potential inconsistencies in server clocks in a distributed environment, numerical version numbers are generally more reliable than timestamps.

## 6. Optimistic Locking - CAS (Compare And Swap)

✅ Concept: It is a CPU atomic instruction that guarantees the atomicity of modifications to shared variables by multiple threads without using traditional locks (synchronized).

### 6.1 Core Principles

1️⃣ V (Memory Value): The actual current value in memory.

2️⃣ E (Expected Value): The expected original value (the value previously read by the thread).

3️⃣ N (New Value): The new value to be updated.

**Execution Logic**: When a thread attempts to update a variable:

* If $V == E$: This means the variable has not been modified by other threads; update $V$ to $N$ directly and return success.

* If $V \neq E$: This means the variable has been modified by other threads; the current thread abandons the update (or enters a spin retry), and returns failure.

### 6.2 Three Major Defects

#### 6.2.1 ABA Problem

* **Phenomenon**: Thread 1 reads value A. Thread 2 then changes the value to B, and then back to A. Thread 1 checks and finds it's still A, assuming nothing has changed, and executes successfully.

* **Impact**: In some scenarios (such as node reuse in linked lists and stacks), this can lead to logical errors.

* **Solution**: Add a version number or timestamp. Java provides `AtomicStampedReference`, which compares not only values ​​but also "stamps".

#### 6.2.2 High Spin Overhead

* **Phenomenon**: Under high concurrency, if many threads compete for the same variable, CAS will fail for a long time, causing the while loop to continuously spin.

* **Impact**: Extremely consumes CPU.

* **Solution**:

① Adaptive Spin: Limit the number of retries.

② Segmented Locking: Java 8 introduced `LongAdder`. It splits a variable into multiple cells, with different threads modifying different cells, and finally sums them, thus distributing competition.

#### 6.2.3 Only Guarantees Atomicity of One Variable

* **Phenomenon**: CAS can only perform atomic operations on a single memory address.

* **Solution**: If you need to guarantee the atomicity of multiple variables, you can encapsulate them into an object and use AtomicReference to perform CAS on the entire object.
#### 6.2.4 CAS vs Synchronized
| **Dimension**            | **CAS (Optimistic)**    | **Synchronized (Pessimistic)** |
| ------------------------ | ----------------------- | ------------------------------ |
| **Thread State**         | Non-blocking, the thread is always running.                   | Blocking, threads that don't acquire the lock are suspended.        |
| **High Lock Contention** | Performance decreases (high CPU consumption due to spinning). | More stable performance (threads are suspended, not consuming CPU). |
| **Low Lock Contention**  | Extremely high performance (direct hardware manipulation).    | Lower performance (despite optimizations, there is still overhead). |



## 7. Optimistic Locking - Atomic Class

**Concept**: The Atomic class utilizes CAS operations to provide a **lock-free** thread-safe mechanism, which typically outperforms synchronized.
| **Category**        | **Common Classes**  | **Description**     |
| ------------------- | ------------------- | ------------------- |
| **Primitive Types** | `AtomicInteger`, `AtomicLong`, `AtomicBoolean` | Atomically update basic variables.                                         |
| **Array Types**     | `AtomicIntegerArray`, `AtomicReferenceArray`   | Atomically update elements in an array.                                    |
| **Reference Types** | `AtomicReference`, `AtomicStampedReference`    | Atomically update object references (the latter resolves the ABA problem). |
| **Field Updater**   | `AtomicIntegerFieldUpdater`                    | Atomically update `volatile` fields in a class using reflection.           |


### 7.1 Underlying Principles

**Core Principles**: CAS + Unsafe + volatile

1️⃣ volatile: Guarantees the visibility of variables across multiple threads, ensuring that each thread reads the latest value.

2️⃣ Unsafe class: Encapsulates low-level operating system instructions, allowing direct manipulation of memory data.

3️⃣ CAS instruction: Implements "compare and swap" using atomic CPU instructions (such as cmpxchg on x86).

```java 
import java.util.concurrent.atomic.AtomicInteger;

public class AtomicCounter {
    // Use AtomicInteger to ensure atomicity
    private AtomicInteger count = new AtomicInteger(0);

    // Increment method
    public void increment() {
        // Equivalent to count++, but atomic
        count.getAndIncrement(); 
    }

    // Get the current count value
    public int getCount() {
        return count.get();
    }
}

```

❓ Why not use **synchronized**? 
| **Lock Type**    | **Description**    |
| ---------------- | ------------------ |
| **synchronized** | **Pessimistic lock**, causes thread context switching (entering kernel mode).  |
| **Atomic**       | **Optimistic lock**, the thread performs the operation in **user mode** through spinning, with minimal overhead. |


### 7.2 Solving the ABA Problem
AtomicStampedReference solves this problem by introducing a Stamp (version stamp):
```java 
// Initial value 100, version stamp 1
AtomicStampedReference<Integer> asr = new AtomicStampedReference<>(100, 1);

// Get the current version (stamp) and reference value
int oldStamp = asr.getStamp(); // Get the current version (stamp)
Integer oldRef = asr.getReference(); // Get the current value (reference)

// CAS operation: Compare and Set the value, also comparing and updating the version stamp
boolean success = asr.compareAndSet(oldRef, 200, oldStamp, oldStamp + 1);

```
### 7.3 High-Performance Concurrency Tool: LongAdder
Under extremely high concurrency, a large number of threads simultaneously competing for the same AtomicLong can lead to numerous CAS failures and spinning, wasting CPU time. Java 8 introduced LongAdder:

✅Core Idea: Segmented Accumulation.

* Internally, it maintains an array of Cells, distributing the competition across multiple variables.

* During reading, it sums the values ​​of all Cells and returns the result.

🧱Comparison Conclusion:

* Low Concurrency: AtomicLong performs better.

* High Concurrency: LongAdder significantly outperforms AtomicLong (throughput is several times higher).

### 7.4 Use Cases

* Use AtomicInteger for simple counting.

* Use LongAdder for high-concurrency summation.

* Use AtomicReference for object modification.

## 8. Optimistic Locking - Optimistic Reads of Java 8's StampedLock

All lock acquisition operations of `StampedLock` return a Stamp, representing the lock's state version.

### 8.1 Underlying Principles

`StampedLock` is not directly based on AQS, but maintains its own similar waiting queue.

* Stamp Composition: It is a long type. The lower 8 bits represent the lock's state (read lock count or write lock holding state), and the higher bits represent the version number.

* validate Logic: validate(stamp) essentially compares the current lock version number with the version number when you acquired it. If they don't match, it means a write operation occurred during this period (a write operation changes the version number).

⚠️ Fatal Warning: Do not use interrupts in StampedLock.

StampedLock.readLock() and writeLock() internally use spin-like logic. If a thread is interrupted while waiting for a lock, CPU usage may spike to 100%. If interruption is required, always use `readLockInterruptibly()`.

### 8.2 Three Access Modes

#### ① Optimistic Reading

📍 No lock is acquired; only a version number is obtained.

* Features: Does not block write locks. Write threads can modify data while reading.

* Safety: After reading, `validate(stamp)` must be called to check if the data has been modified during the read operation.

#### ② Pessimistic Reading

* Features: Multiple threads can hold the lock simultaneously, but it blocks write locks.

#### ③ Write Lock

* Features: Exclusive, completely mutually exclusive.

### 8.3 Use Cases

* Recommended scenarios: Read-heavy, write-light scenarios with extremely high performance requirements.

* Use with caution: in scenarios with complex code logic, requiring reentrant locks, or with strict requirements for interrupt handling.
