# Threads, Multithreading

Multithreading improves program parallelism and performance by allowing multiple threads to execute concurrently, fully utilizing the performance of multi-core CPUs. A thread is the basic unit of program execution, while a process contains multiple threads. In Java, there are several ways to implement threads; the most suitable method can be chosen based on actual needs.

## 1. Core Concepts: Process vs. Thread

### 1.1 Basic Concepts

* **Thread (Thread):** The smallest unit of CPU scheduling, an execution unit within a process. A process can contain multiple threads that share the process's memory resources (heap and method area) but have independent stacks.

* **Process (Process):** The smallest unit of resource allocation by the operating system; multiple threads within a process constitute an execution unit.

### 1.2 Thread Lifecycle

**① New (New):** A thread object has been created, but `start()` has not yet been called; it has not yet started.

**② Runnable (Ready/Running):** Executing in the JVM, possibly waiting for system resources (such as the CPU).

**③ Blocked:** Waiting to acquire the monitor lock (synchronized) (The thread is blocked due to certain conditions (such as I/O operations), waiting for that condition to be met).

**④ Waiting:** Waiting indefinitely for another thread to perform a specific operation (wait, join).

**⑤ Timed_Wating:** Waiting for a specified time (sleep(ms), wait(ms)).

**⑥ Terminated:** The thread has finished executing.

⚠️ **Thread Creation:** Java only has one way to create a thread: `new Thread().start()`. Regardless of other multithreading creation methods, they all ultimately rely on this method.

⚠️ **Thread Execution:** After creating a new Thread, calling the `start()` method automatically executes the `run()` method. Directly executing the `run()` method will treat it as a regular method, not a multithreaded operation.

⚠️ **Thread Waiting:** Thread.sleep() and Object.wait()
| **Feature**  | **Thread.sleep()** | **Object.wait()**  |
| ------------- | ---------------- | --------------------|
| **Belongs to** | `java.lang.Thread` (static method)   | `java.lang.Object` (instance method) |
| **Lock Resource Release** | Does not release the lock, "sleeps" while holding the lock | Releases the lock, gives up execution rights to others for competition |
| **Usage Restriction**     | Can be called anywhere   | Must be called within a synchronized block or method   |
| **Wake-up Condition**     | Automatically wakes up after the specified time  | Must wait for `notify()`/`notifyAll()` or timeout |
| **Thread State**          | `TIMED_WAITING`   | `WAITING` or `TIMED_WAITING`          |
| **Main Purpose**          | Pauses execution, polling wait  | Thread communication, Producer-Consumer model  |
| **Lock Behavior**         | "Holds the lock but does nothing"  | "Waits for permission to proceed, releases the lock"  |
| **When to Use**           | When you simply want the current thread to slow down or simulate basic timing | When multiple threads need to cooperate, such as in the Producer-Consumer problem |


### 1.3 Thread Context Switching

Thread context switching is a core mechanism of multitasking operating systems. It allows the CPU to quickly switch between multiple threads, creating the illusion that multiple programs are "running simultaneously."

#### 1.3.1 Thread Context

Context refers to all the environmental information that the CPU relies on when executing a thread.

It mainly includes the following:

① Register state: Including general-purpose registers, program counter (PC, pointing to the next instruction), stack pointer (SP), etc.

② Kernel stack: Each thread has its own stack when executing in kernel mode.

③ User stack: Local variables and function call information of a thread when executing in user mode.

#### 1.3.2 Basic Switching Process

1️⃣ Save context: Save the current register values, program counter, and other information of thread A to the thread's control block (TCB) or kernel stack.

2️⃣ Scheduling Switch: The operating system scheduler selects the next thread B to run based on an algorithm (such as time-slice round-robin or priority).

3️⃣ Context Restoration: The previously saved state is read from thread B's control block and loaded into the CPU registers.

4️⃣ Execution Jump: Based on the restored program counter, execution jumps to the point where thread B last stopped and continues execution.

#### 1.3.3 Scenarios Triggering Switching

* Time slice expires: To ensure fairness, the operating system forcibly removes the execution rights of time-consuming threads.

* Active suspension: The thread calls sleep(), wait(), or yield().

* Blocking wait: The thread is waiting for I/O read/write, acquiring a lock, or a network response.

* Hardware interrupt: A peripheral device (such as a hard drive or network card) completes its task and sends an interrupt signal, forcing the system to switch to the interrupt handler.

#### 1.3.4 Precautions

⚠️ Frequent context switching can lead to decreased system performance, primarily due to the following reasons:

**①** The CPU instruction time required to save and restore registers and update kernel data structures (scheduling list).

**②** Cache Miss:** Data in thread A's L1/L2 cache is initially in the CPU's L1/L2 cache. After switching to thread B, B needs to reread the data from memory, causing a sharp drop in cache hit rate.

**③**TLB Flush:** If the switch involves threads from different processes, the page table cache (TLB) will be flushed, slowing down virtual address translation.

🧠 Reduce context switching:

**①** Lock-free programming:** Use CAS (Compare and Swap) algorithms instead of traditional mutexes to prevent threads from entering a blocked state due to lock contention.

**②** Coroutines:** Switching is implemented in user space, requiring no kernel involvement and incurring minimal overhead (e.g., Go's Goroutines). **③ Properly Configure the Number of Threads:** More threads are not always better. Generally, for CPU-intensive tasks, the number of threads should equal the number of CPU cores; for I/O-intensive tasks, the number can be increased appropriately, but a balance needs to be found through load testing.

**④** Use Spinlocks: If the estimated lock occupancy time is extremely short, having threads "wait" in a loop instead of suspending them directly can save two context switches.

## 2. Multithreading

### 2.1 Basic Concepts

#### 2.1.1 Concurrency vs. Parallelism

* Concurrency: Two or more jobs execute within the same **time period**.

* Parallelism: Two or more jobs execute at the same **moment**.

#### 2.1.2 Synchronous vs. Asynchronous

* Synchronous: After a call is made, it cannot return until a result is received; it waits indefinitely.

* Asynchronous: After a call is made, it does not wait for a result; it returns immediately.

### 2.2 Thread Deadlock

Deadlock occurs when two or more threads are locked in a deadlock due to contention for resources. Without external intervention, they will all be unable to proceed.

#### 2.2.1 Four Necessary Conditions
Deadlock occurs only when all four of the following conditions are met simultaneously:

**① Mutual Exclusion:** The resource is exclusively held by one thread at a time (e.g., a synchronized lock).

**② Hold and Wait:** A thread already holds at least one resource but requests a new resource that is already held by another thread. The requesting thread is blocked but holds onto its existing resources.

**③ No Preemption:** Resources held by a thread cannot be forcibly taken away by another thread before the thread has finished using them; the thread must release the resource itself.

**④ Circular Wait:** A circular chain of threads exists. For example: Thread A waits for a resource held by Thread B, Thread B waits for a resource held by Thread C, and Thread C waits for a resource held by Thread A.

**Example**:

🎯 Phenomenon: After printing "Attempting to lock..." to the console, nothing happens again; the program never terminates.
```java
public class DeadlockDemo {
    private static Object resourceA = new Object();
    private static Object resourceB = new Object();

    public static void main(String[] args) {
        // Thread 1: Locks A, tries to lock B
        new Thread(() -> {
            synchronized (resourceA) {
                System.out.println("Thread 1: Locked A");
                try { Thread.sleep(100); } catch (Exception e) {} // Ensures Thread 2 locks B
                
                System.out.println("Thread 1: Trying to lock B...");
                synchronized (resourceB) {
                    System.out.println("Thread 1: Successfully locked B");
                }
            }
        }).start();

        // Thread 2: Locks B, tries to lock A
        new Thread(() -> {
            synchronized (resourceB) {
                System.out.println("Thread 2: Locked B");
                try { Thread.sleep(100); } catch (Exception e) {}
                
                System.out.println("Thread 2: Trying to lock A...");
                synchronized (resourceA) {
                    System.out.println("Thread 2: Successfully locked A");
                }
            }
        }).start();
    }
}

```

#### 2.2.3 Deadlock Prevention Breaking one of the four necessary conditions for deadlock will solve the problem:

① Break **circular wait**: Fix the locking order (most common) Ensure all threads acquire resources in the same order. For example, regardless of the thread, it must lock A before locking B.
```java
public class DeadlockDemo {
    private static Object resourceA = new Object();
    private static Object resourceB = new Object();

    public static void main(String[] args) {
        // Thread 1: Lock A, then attempt to lock B
        new Thread(() -> {
            synchronized (resourceA) {
                System.out.println("Thread 1: Locked A");
                try { Thread.sleep(100); } catch (Exception e) {} // Ensure Thread 2 locks B
                
                System.out.println("Thread 1: Trying to lock B...");
                synchronized (resourceB) {
                    System.out.println("Thread 1: Successfully locked B");
                }
            }
        }).start();

        // Thread 2: Lock A, then attempt to lock B (breaking the circular wait condition)
        new Thread(() -> {
            synchronized (resourceA) { // Changed the order of locking: lock A first
                System.out.println("Thread 2: Locked A");
                try { Thread.sleep(100); } catch (Exception e) {}

                System.out.println("Thread 2: Trying to lock B...");
                synchronized (resourceB) {
                    System.out.println("Thread 2: Successfully locked B");
                }
            }
        }).start();
    }
}

```
② Disrupt **Request and Hold**: Request all resources at once. Instead of requesting a new lock while holding a lock, try to acquire all the necessary locks at once.

```java 
public class DeadlockDemo {
    private static Lock resourceA = new ReentrantLock();
    private static Lock resourceB = new ReentrantLock();

    public static void main(String[] args) {
        // Thread 1: Try to lock A and B at once
        new Thread(() -> {
            try {
                if (resourceA.tryLock() && resourceB.tryLock()) {
                    System.out.println("Thread 1: Successfully locked A and B");
                    try {
                        // Thread 1 performs task
                        Thread.sleep(100);
                    } finally {
                        resourceA.unlock();
                        resourceB.unlock();
                    }
                } else {
                    System.out.println("Thread 1: Failed to acquire required resources, retrying");
                }
            } catch (InterruptedException e) {
                e.printStackTrace();
            }
        }).start();

        // Thread 2: Try to lock A and B at once
        new Thread(() -> {
            try {
                if (resourceA.tryLock() && resourceB.tryLock()) {
                    System.out.println("Thread 2: Successfully locked A and B");
                    try {
                        // Thread 2 performs task
                        Thread.sleep(100);
                    } finally {
                        resourceA.unlock();
                        resourceB.unlock();
                    }
                } else {
                    System.out.println("Thread 2: Failed to acquire required resources, retrying");
                }
            } catch (InterruptedException e) {
                e.printStackTrace();
            }
        }).start();
    }
}
```

③ Breaking **non-preemption**: Using tryLock(). Use ReentrantLock's tryLock(time, unit). If the attempt to acquire the lock times out, it proactively releases the lock it already holds, backtracks, and retryes.
```java
public class DeadlockDemo {
    private static Lock resourceA = new ReentrantLock();
    private static Lock resourceB = new ReentrantLock();

    public static void main(String[] args) {
        // Thread 1: Try to acquire resources A and B; if timeout, release the acquired resources
        new Thread(() -> {
            try {
                boolean gotA = resourceA.tryLock();
                if (gotA) {
                    System.out.println("Thread 1: Successfully locked A");
                    try {
                        // Wait long enough to simulate acquiring resource B
                        boolean gotB = resourceB.tryLock();
                        if (gotB) {
                            System.out.println("Thread 1: Successfully locked B");
                            // Thread 1 performs task
                            Thread.sleep(100);
                        } else {
                            System.out.println("Thread 1: Failed to acquire B, releasing A and retrying");
                            resourceA.unlock(); // Release A
                            Thread.sleep(100); // Pause for a while
                        }
                    } finally {
                        if (resourceB.isHeldByCurrentThread()) {
                            resourceB.unlock();
                        }
                    }
                }
            } catch (InterruptedException e) {
                e.printStackTrace();
            }
        }).start();

        // Thread 2: Try to acquire resources A and B; if timeout, release the acquired resources
        new Thread(() -> {
            try {
                boolean gotA = resourceA.tryLock();
                if (gotA) {
                    System.out.println("Thread 2: Successfully locked A");
                    try {
                        // Wait long enough to simulate acquiring resource B
                        boolean gotB = resourceB.tryLock();
                        if (gotB) {
                            System.out.println("Thread 2: Successfully locked B");
                            // Thread 2 performs task
                            Thread.sleep(100);
                        } else {
                            System.out.println("Thread 2: Failed to acquire B, releasing A and retrying");
                            resourceA.unlock(); // Release A
                            Thread.sleep(100); // Pause for a while
                        }
                    } finally {
                        if (resourceB.isHeldByCurrentThread()) {
                            resourceB.unlock();
                        }
                    }
                }
            } catch (InterruptedException e) {
                e.printStackTrace();
            }
        }).start();
    }
}
```

### 2.3 ThreadLocal

✅ A special type of variable provided by Java. Its core idea is to provide each thread with an independent copy of the variable.

**synchronized**: Used to make multiple threads queue to access shared variables;

**ThreadLocal**: Trades space for time, allowing each thread to access only its own private copy, thus completely avoiding contention.

#### 2.3.1 Underlying Principles

**① Data is stored in Thread**: Each Thread object has a member variable named `threadLocals`, which is of type `ThreadLocalMap`.

**② ThreadLocalMap**: This is a structure similar to a HashMap. Its key is the ThreadLocal object itself, and its value is the value we want to store.

**③ Weak Reference**: In a ThreadLocalMap, the Entry references the key with a weak reference, while the reference to the value is a strong reference.

⚠️ Weak Reference VS Strong Reference
| **Characteristics**  | **Strong Reference**  | **Weak Reference** |
| ---------------------| ---------------------- | ----------------- |
| **Object Lifecycle** | As long as a strong reference exists, the object will not be garbage collected. | An object will be garbage collected even if it has a weak reference, as long as it doesn't have a strong reference. |
| **Garbage Collection Behavior** | The object will not be garbage collected while there is a strong reference. | The object will be garbage collected during the next garbage collection, even if a weak reference exists. |
| **Typical Applications** | Regular object references; most objects in a program use strong references.     | Scenarios where objects need to be reclaimed at any time, such as caching, object pools, and listeners. |
| **Common Classes** | Ordinary object references  | `WeakReference<T>` |


#### 2.3.2 Memory Leak

Because the Key of ThreadLocalMap is a weak reference, if the ThreadLocal object has no external strong references pointing to it, the Key will be garbage collected during GC, at which point the Key becomes null.

However, the Value is a strong reference. As long as the thread is not destroyed (for example, in a thread pool, the thread will be reused), the Value corresponding to this null value will remain in memory and cannot be garbage collected, thus causing a memory leak.

💡**Memory Leak**: During program execution, the program fails to properly release memory that is no longer in use, causing this memory to be unable to be reused, which may eventually exhaust the system's memory resources, leading to decreased program performance or even crashes.

🧠**Solution**: Always call the remove() method after using ThreadLocal.
```java 
try {
    threadLocal.set(data);  // Set data in ThreadLocal for the current thread
    // Business logic (some operations that might use the thread-local data)
} finally {
    threadLocal.remove();  // Explicitly remove the data to prevent memory leaks
}

```

#### 2.3.3 Passing ThreadLocal Values ​​Across Threads

##### ① InheritableThreadLocal (JDK Built-in)

✅Suitable for scenarios involving parent and child threads (i.e., creating a new Thread() in the current thread).

* **Principle**: When a child thread is created, it copies all data from the parent thread's inheritableThreadLocals variable pool.

* **Limitations**: Copying only occurs when the thread is created. In a thread pool environment, threads are reused and not recreated, therefore the new value at the moment the task is submitted cannot be obtained.
```java
ThreadLocal<String> threadLocal = new InheritableThreadLocal<>();
threadLocal.set("父线程的值");

new Thread(() -> {
    System.out.println("子线程获取: " + threadLocal.get()); // 可以获取到
}).start();
```
##### ② TransmittableThreadLocal (TTL, Alibaba open source, highly recommended)

✅ Solves the problem of InheritableThreadLocal values ​​becoming outdated due to thread pool reuse.

**Principle**: It uses a "capture" and "replay" mechanism to capture the value of the current thread when a task is submitted, inject it into the executing thread before task execution, and restore it after execution.

1️⃣ Declare variables using TransmittableThreadLocal.

2️⃣ Use TtlExecutors to decorate the thread pool.
```java 
// 1. Definition
TransmittableThreadLocal<String> context = new TransmittableThreadLocal<>();
context.set("My Information");

// 2. Decorate the Thread Pool
Executor executor = TtlExecutors.getTtlExecutor(existingExecutor);

executor.execute(() -> {
    System.out.println(context.get()); // Even when the thread pool is reused, the latest value can still be accessed
});

```
##### ③ Manual explicit passing (most primitive but reliable) 

Pass the value through the constructor or closure before submitting the task, and then manually set it during execution.
```java
String value = threadLocal.get(); // 1. Get value from the main thread
executor.execute(() -> {
    try {
        threadLocal.set(value);   // 2. Set value in the child thread
        // Business logic...
    } finally {
        threadLocal.remove();     // 3. Must clean up to prevent memory leaks and contamination
    }
});

```

📅**Load Testing Traffic Tagging**: In load testing scenarios, ThreadLocal is used to store load testing tags to distinguish load testing traffic from real traffic. If the tags are lost, load testing traffic may be incorrectly treated as production traffic.

📅**Context Passing**: In distributed systems, this is used to pass trace information (such as Trace ID) or user context information.

##### ② Commonly Used Methods

* start(): Starts the thread. After calling `start()`, the thread enters the ready state (awaiting CPU scheduling).

* run(): The task to be executed by the thread. The `run()` method needs to be overridden.

* sleep(long millis): Pauses the thread for the specified time (milliseconds).

* join(): Waits for the thread to finish executing. The current thread will wait for the thread that called it to finish before continuing execution.

* setPriority(int priority): Sets the thread priority.

* getName(): Gets the thread name.

##### ③ Advantages and Disadvantages

* **Advantages**: Simple code writing; the current thread can be obtained directly through `this`.

* **Disadvantages**: Java uses a single inheritance mechanism; if you inherit from `Thread`, you cannot inherit from other classes, resulting in poor flexibility.

#### 2.4.2 Implementing the `Runnable` Interface

Unlike inheriting the `Thread` class, the `Runnable` interface provides greater flexibility. Create a class that implements the `Runnable` interface and override the `run()` method. Start the thread by passing a `Runnable` object to the constructor of the `Thread` class.

##### ① Steps

1️⃣ Create a thread class that implements the `Runnable` interface.

2️⃣ Implement the `run()` method to define the thread task.

3️⃣ Create a custom thread class object that implements the `Runnable` interface.

4️⃣ Create a `Thread` object and pass the `Runnable` object as a parameter.

5️⃣ Call `start()` to start the thread.
```java
// 1. Create a thread class that implements the Runnable interface
class MyRunnable implements Runnable {
    // 2. Implement the `run()` method to define the thread task
    @Override
    public void run() {
        for (int i = 0; i < 10; i++) {
            System.out.println(Thread.currentThread().getName()); // Print the current thread's name
            System.out.println("i = " + i);                        // Print the value of i
        }
    }
}

public class Main {
    public static void main(String[] args) {
        // 3. Create an instance of the custom class that implements the `Runnable` interface
        MyRunnable myRunnable = new MyRunnable();
        
        // 4. Create `Thread` objects and pass the `Runnable` instance as a parameter
        Thread t1 = new Thread(myRunnable);
        // 5. Call `start()` to start the thread.
        t1.start();

        // Create another thread and start it
        Thread t2 = new Thread(myRunnable);
        t2.start();
    }
}

```

##### ②Implementing the `Runnable` interface vs. inheriting the `Thread` class
| **Characteristics** | **Inheriting `Thread` Class**  | **Implementing `Runnable` Interface** |
| ------------------- | ------------------------ | ------------------------------------------- |
| **Inheritance**     | Can only inherit from the `Thread` class (due to the single inheritance limitation) | Can inherit from other classes and implement multiple interfaces                  |
| **Task and Thread** | Task and thread are bound in the same class | Task and thread are separated; tasks can be shared by multiple threads            |
| **Performance**     | Suitable for simple scenarios  | Slightly better performance, suitable for thread pools and more complex scenarios |
| **Thread Pool**     | Not suitable for use with thread pools   | More convenient for use with thread pools, ideal for high-concurrency scenarios   |
| **Flexibility**     | Less flexible  | Tasks and threads can be decoupled, allowing multiple threads to share tasks      |

#### 2.4.3 Implementing the `Callable` and `Future` Interfaces

The `Callable` and `Future` interfaces are often used in conjunction with thread pools (`ExecutorService`). They provide more powerful functionality than `Runnable`, especially in scenarios where tasks have return values.

##### ① Usage Steps

1️⃣ Create a task class that implements the `Callable` interface and implements the `call()` method.

2️⃣ Submit the `Callable` task using `ExecutorService`.

3️⃣ Obtain the task's execution result or status through the `Future` object.

```java 
 // 1. Create a task class that implements the `Callable` interface and implements the `call()` method. 
class FactorialTask implements Callable<Long> {
    private long n;

    public FactorialTask(long n) {
        this.n = n;
    }

    // Implement the call() method
    @Override
    public Long call() {
        long result = 1;
        for (long i = 1; i <= n; i++) {
            result *= i;
        }
        return result;
    }
}

public class Main6 {
    public static void main(String[] args) {
        // Create a thread pool
        ExecutorService executor = Executors.newFixedThreadPool(5);

        // Create task
        FactorialTask task1 = new FactorialTask(5);
        FactorialTask task2 = new FactorialTask(10);

        // Submit a task to obtain a Future object
        Future<Long> future1 = executor.submit(task1);
        Future<Long> future2 = executor.submit(task2);



        // Get task results
        try {
            long result1 = future1.get();
            long result2 = future2.get();

            System.out.println("Result1: " + result1);
            System.out.println("Result2: " + result2);
        } catch (ExecutionException | InterruptedException e) {
            throw new RuntimeException(e);
        }
    }
}
```
Or
```java
public static void main(String[] args) {
    // 1. Create a Callable implementation (using Lambda expression)
    Callable<Integer> task = () -> {
        System.out.println("Child thread is calculating...");
        Thread.sleep(2000); // Simulate time-consuming operation
        return 100 + 200;
    };

    // 2. Wrap the Callable with FutureTask
    FutureTask<Integer> futureTask = new FutureTask<>(task);

    // 3. Submit the FutureTask to a Thread for execution
    Thread thread = new Thread(futureTask);
    thread.start();

    System.out.println("Main thread continues doing other work...");

    try {
        // 4. Get the result. Note: get() will block the main thread until the child thread finishes
        Integer result = futureTask.get();
        System.out.println("Calculation result: " + result);
    } catch (InterruptedException | ExecutionException e) {
        e.printStackTrace();
    }
}

```
##### ② Commonly Used Methods

* **call()**: The task method of `Callable`. Unlike `run()`, `call()` can return a value.

* **cancel()**: Cancels task execution.

* **get()**: Retrieves the execution result of the task.

* **get(long timeout, TimeUnit unit)**: Throws a `TimeoutException` if the task is not completed within the specified time.

* **isDone()**: Checks if the task is completed.

* **isCancelled()**: Checks if the task has been cancelled.

#### 2.4.4 Creating a Thread Pool Using the `Executor` Framework

The `Executor` framework manages threads through thread pools, avoiding the hassle of directly creating and destroying threads. `ExecutorService` provides more efficient thread management.

##### ① Usage Steps

1️⃣ Create an `ExecutorService` thread pool.

2️⃣ Submit tasks (Runnable or Callable) to the thread pool.

3️⃣ Manage the lifecycle of the thread pool, such as shutting it down.

```java
class MyRunnable implements Runnable {
    @Override
    public void run() {
        System.out.println(Thread.currentThread().getName() + " is running");
    }
}

public class Main {
    public static void main(String[] args) {
        ExecutorService executorService = Executors.newFixedThreadPool(2);  // Create a thread pool with 2 threads
        
        executorService.submit(new MyRunnable());  // Submit a task to the thread pool
        executorService.submit(new MyRunnable());  // Submit another task to the thread pool
        
        executorService.shutdown();  // Shut down the thread pool
    }
}

```

### 2.5 Thread Pools

In Java concurrent programming, thread pools (ThreadPool) are the best practice for managing threads. They avoid the performance overhead of frequently creating and destroying threads through "pooling technology," while effectively controlling the number of concurrent threads in the system.

#### 2.5.1 Thread Pools VS Manually creating new Thread()
| **Comparison Dimension** | **`new Thread()` (Manual Creation)** | **Thread Pool (`ExecutorService`)**  |
| --------------------------- | --------------------------------- | ------------------------------- |
| **Resource Consumption**    | High. A new thread is created for each task, and old threads are destroyed, wasting memory and CPU.                                | Low. Core threads can be reused, avoiding the overhead of frequently creating and destroying threads.                    |
| **Response Speed**          | Slow. Tasks must wait for thread creation before execution.                                                                        | Fast. Tasks are executed immediately by idle threads in the pool.                                                        |
| **Thread Management**       | None. There’s no control over the total number of threads, and too many threads can lead to OOM (Out of Memory) or system crashes. | Strong. You can control the maximum number of concurrent threads, support task queuing, timed execution, and monitoring. |
| **Lifecycle**               | Short. Threads are destroyed after task completion, treated as one-time resources.                                                 | Configurable. Threads can be kept alive or dynamically destroyed based on idle time.                                     |
| **Functionality Expansion** | Simple. Only the basic `start()` method is available.                                                                              | Rich. Provides features like scheduled execution, periodic tasks, and task rejection strategies.                         |


#### 2.5.2 7 Core Parameters (ThreadPoolExecutor)

```java

public ThreadPoolExecutor(

int corePoolSize, // 1. Core thread count. These threads will not be destroyed even when there are no tasks.

int maximumPoolSize, // 2. Maximum thread count. The maximum number of threads allowed by the thread pool.

long keepAliveTime, // 3. Temporary thread survival time. The survival time of non-core threads (temporary threads) when idle.

TimeUnit unit, // 4. Time unit. The time unit for the survival time.

BlockingQueue<Runnable> workQueue, // 5. Task queue. A blocking queue that stores tasks to be executed.

ThreadFactory threadFactory, // 6. Thread factory. A factory used to create threads, usually used to give threads a nice name.

RejectedExecutionHandler handler // 7. Rejection policy. How to handle new tasks when the queue and threads are full.

)
```
#### 2.5.3 Workflow

1️⃣ Thread pool initialization: Create **core thread count** threads.

2️⃣ If the number of submitted tasks exceeds the core thread count, the thread pool will place the tasks in a queue.

3️⃣ If the queue is full and the current thread count has not yet reached the **maximum thread count**, a new thread will be created to execute the task.

4️⃣ If the queue is full and the current thread count has reached the **maximum thread count**, a rejection policy will be implemented.

5️⃣ Non-core threads will be destroyed after being idle for more than the **idle thread lifespan**. 

```java 
public class ThreadPoolDemo {
    public static void main(String[] args) {
        // 1. Manually create a thread pool
        ExecutorService executor = new ThreadPoolExecutor(
            2,                      // corePoolSize: number of core threads (permanent threads)
            5,                      // maximumPoolSize: maximum number of threads (including temporary workers)
            60L,                    // keepAliveTime: how long temporary workers are kept idle before being removed
            TimeUnit.SECONDS,       // unit: time unit for keepAliveTime
            new LinkedBlockingQueue<>(3), // workQueue: "waiting room" for tasks (with capacity of 3)
            Executors.defaultThreadFactory(), // threadFactory: way of creating threads (default factory)
            new ThreadPoolExecutor.CallerRunsPolicy() // handler: rejection policy when there are too many tasks
        );

        // 2. Submit tasks to the pool
        for (int i = 1; i <= 10; i++) {
            final int taskId = i;
            executor.execute(() -> {
                System.out.println(Thread.currentThread().getName() + " is executing task " + taskId);
                try {
                    Thread.sleep(500); // Simulate business processing
                } catch (InterruptedException e) {
                    e.printStackTrace();
                }
            });
        }

        // 3. Shutdown the thread pool (graceful shutdown)
        executor.shutdown();
    }
}

```

#### 2.5.4 Rejection Policies

* **AbortPolicy (Default)**: Throws a RejectedExecutionException, preventing system execution.

* **CallerRunsPolicy**: Executes the task submitted by the caller thread (returning the task to the caller thread for processing), which can slow down task submission.

* **DiscardOldestPolicy**: Discards the oldest task (at the front of the queue) and attempts to submit it again.

* **DiscardPolicy**: Discards the task directly without processing or reporting an error.

#### 2.5.5 Common Thread Pools
| **Thread Pool Type**     | **Characteristics**    | **Potential Risks**    |
| ------------------------ | ---------------------- | ---------------------- |
| **FixedThreadPool**      | A thread pool with a fixed number of threads. Suitable for handling a large number of short-lived tasks.              | Infinite queue length, which may lead to **Out of Memory (OOM)** if tasks pile up.       |
| **SingleThreadExecutor** | A thread pool with only one thread, tasks are executed sequentially.                                                  | Infinite queue length, tasks may backlog and cause **OOM** if the queue grows too large. |
| **CachedThreadPool**     | A thread pool that creates threads as needed. Suitable for handling a large number of short-lived asynchronous tasks. | Creating too many threads may lead to **OOM** due to excessive memory usage.             |
| **ScheduledThreadPool**  | A thread pool that supports scheduling tasks, including fixed-rate or fixed-delay executions.                         | Too many threads could exhaust system resources and cause instability.                   |

##### ①newFixedThreadPool()

A fixed-size thread pool is created, ensuring the number of threads will not exceed the set value. Idle threads will continue to exist until the thread pool is explicitly shut down. If the number of tasks exceeds the thread pool capacity, the tasks will be placed in a task queue to await execution.

```java
public static void main(String[] args) {
    ExecutorService executor = Executors.newFixedThreadPool(10);

    // Submit Task
    for (int i = 0; i < 15; i++) {
        final int taskId = i;
        executor.submit(() -> {
            System.out.println("Execute task: " + taskId + ", Thread: " +
                    Thread.currentThread().getName());
            try {
                Thread.sleep(1000);
            } catch (InterruptedException e) {
                e.printStackTrace();
            }
        });
    }
    executor.shutdown();
}
```

#####  ② newCachedThreadPool()

Create a cacheable thread pool where threads can be dynamically created as needed, and idle threads are reclaimed after 60 seconds. This approach may create a large number of threads when there are many tasks and they are executed frequently, making it suitable for tasks with an variable number of executions.

```java
public static void main(String[] args) {
    ExecutorService executor = Executors.newCachedThreadPool();

    // Submit Task
    for (int i = 0; i < 15; i++) {
        final int taskId = i;

                    Thread.currentThread().getName());
            try {
                Thread.sleep(1000);
            } catch (InterruptedException e) {
                e.printStackTrace();
            }
        });
    }
    executor.shutdown();
}
```

#####  ③ newSingleThreadExecutor()

This creates a single-threaded thread pool with only one worker thread, where all tasks are executed sequentially. If a task throws an exception, the thread pool terminates, and subsequent tasks will not be executed. It is suitable for tasks that need to be executed sequentially.

```java
public static void main(String[] args) {
    ExecutorService executor = Executors.newSingleThreadExecutor();

    // Submit Task
    for (int i = 0; i < 15; i++) {
        final int taskId = i;
        executor.submit(() -> {
            System.out.println("Execute task: " + taskId + ", Thread: " +
                    Thread.currentThread().getName());
            try {
                Thread.sleep(1000);
            } catch (InterruptedException e) {
                e.printStackTrace();
            }
        });
    }
    executor.shutdown();
}
```

##### ④ newScheduledThreadPool()

It supports scheduling of timed and periodic tasks, and is suitable for executing timed and periodic tasks.

```java
public static void main(String[] args) {
    ScheduledExecutorService executor = Executors.newScheduledThreadPool(2);

    // Execute after a 1-second delay

    executor.schedule(() -> System.out.println("Delayed task executed!"), 1, TimeUnit.SECONDS);

    // Execute every 2 seconds after a 0-second delay
    executor.scheduleAtFixedRate(() -> System.out.println("Scheduled task executed!"), 0, 3, TimeUnit.SECONDS);

    executor.shutdown();
}
```

##### ⑤ newWorkStealingPool()

Suitable for large-scale parallel computing scenarios, where multiple tasks are broken down into multiple subtasks and the workload is balanced through a work-stealing algorithm.


##### ⑥ newThreadPool()

Create a custom thread pool suitable for executing a variable number of tasks.

```java
public static void main(String[] args) {
    // Maximum task queue capacity: 100

    BlockingQueue<Runnable> workQueue = new LinkedBlockingQueue<>(100);

    // Core thread count: 4, maximum thread count: 10, idle thread lifespan: 60 seconds
    ThreadPoolExecutor executor = new ThreadPoolExecutor(4, 10, 60, TimeUnit.SECONDS, workQueue);

    // Submit Task
    for (int i = 0; i < 15; i++) {
        final int taskId = i;
        executor.submit(() -> {
            System.out.println("Execute task: " + taskId + ", Thread: " +
                    Thread.currentThread().getName());
            try {
                Thread.sleep(1000);
            } catch (InterruptedException e) {
                e.printStackTrace();
            }
        });
    }
    executor.shutdown();
}
```

##### ⑦ newForkJoinPool()

This is suitable for divide-and-conquer algorithms, such as splitting a task into multiple subtasks, executing them in parallel, and then merging the results. Using `ForkJoinPool`, a task can be decomposed into subtasks, executed independently, and then the results merged, making it particularly suitable for recursive tasks.

```java
public static void main(String[] args) {
    ForkJoinPool pool = new ForkJoinPool();
    ForkJoinTask<Integer> task = new RecursiveTask<Integer>() {
        @Override
        protected Integer compute() {
            // Divide and conquer computation task
            return 1;
        }
    };
    Integer result = pool.invoke(task);
    System.out.println(result);
    pool.shutdown();
}
```

##### ⑧ newVirtualThreadPool()

A thread pool that creates virtual threads (introduced in Java 19) is suitable for executing a variable number of tasks.
